# Руководство по репозиторию

## Согласование и границы работы

Перед редактированием файлов проекта опишите пользователю предполагаемые изменения
и получите явное согласие. Одобренная реализация автоматически включает
актуализацию относящихся к ней файлов `memory-bank/` и этого руководства, если
изменились общие правила репозитория; отдельное подтверждение для такой
синхронизации не требуется. Если документационное изменение расширяет исходную
задачу или меняет правила работы, запросите отдельное согласие.

Сохраняйте чужие и runtime-изменения рабочего дерева. Не удаляйте, не откатывайте
и не добавляйте их в коммит без явного разрешения пользователя.

## Memory Bank: когда читать и обновлять

В начале существенной задачи прочитайте `AGENTS.md` и
`memory-bank/activeContext.md`. Остальные файлы открывайте только тогда, когда их
назначение связано с задачей:

| Файл | Назначение | Когда читать | Когда обновлять |
|---|---|---|---|
| `projectbrief.md` | Цель и базовые ограничения проекта | Новая функция, смена области или неоднозначность требований | Изменилась цель или ключевые требования |
| `productContext.md` | Пользователи, сценарии и UX-цели | Изменение поведения или интерфейса | Изменился пользовательский сценарий или продуктовая цель |
| `systemPatterns.md` | Архитектура и системные инварианты | Хранение, сеть, обновление, безопасность или архитектура | Принят или изменён системный паттерн |
| `techContext.md` | Стек, структура, сборка, тесты и релизы | Инструменты, зависимости, сборка или публикация | Изменились команды, проекты, пути или окружение |
| `progress.md` | Реализованные возможности и оставшиеся задачи | Планирование и проверка текущих возможностей | Завершена существенная функция или изменился список задач |

`activeContext.md` должен содержать только актуальный фокус, версию, состояние
проверок, блокеры и неопубликованные изменения, а не исторический журнал. После
одобренной реализации пересмотрите только связанные файлы Memory Bank. Не
изменяйте их механически, если факты не поменялись. Сопутствующую документацию
включайте в тот же локальный тематический коммит, что и код.

Код, конфигурация, тесты и фактическое состояние Git имеют приоритет над Memory
Bank. Если найдено расхождение, исправьте устаревшую документацию в рамках
одобренной задачи. Не записывайте в Memory Bank пароли, ключи, реальные данные
библиотеки и другие секреты.

## Структура проекта

Это настольное Windows-приложение учёта библиотеки храма на Free Pascal и
Lazarus. `LibraApp.lpr` и `Library.lpi` — основное приложение;
`LibraryUpdater.lpr` и `LibraryUpdater.lpi` — помощник установки обновлений.
Общие модули находятся в `src/`, формы — в `src/forms/`, тестовые проекты — в
`tests/`, release-скрипт — `scripts/Build-Release.ps1`. Исполняемые файлы и
рабочее окружение находятся в `Prog/`, результаты компиляции — в `lib/`,
релизные архивы — в игнорируемом каталоге `dist/`.

Не изменяйте пользовательские каталоги `Data`, `Covers`, `Backup`, `Logs` и их
варианты внутри `Prog/`, если задача прямо этого не требует. Не коммитьте EXE,
`Library.exe.old`, runtime-копии `INSTALL.md`, данные, журналы, резервные копии и
содержимое `lib/` или `dist/`.

## Локальная разработка и Git

Разрабатывайте локально. Разрешены короткие тематические локальные коммиты с
русскими сообщениями в повелительной форме, например `Исправить проверку
продления выдачи`. Один коммит должен решать одну задачу и включать относящиеся
к ней изменения Memory Bank.

Не выполняйте `git push`, не создавайте и не отправляйте теги и не создавайте
GitHub Releases без отдельного явного указания пользователя. Документационный
коммит можно отправить без бинарного релиза, но только по явной команде.

Перед коммитом проверяйте `git status`, добавляйте в индекс только файлы текущей
задачи и выполняйте `git diff --check`. Не очищайте рабочее дерево за счёт чужих
изменений.

## Сборка и проверка

В этом окружении используйте Lazarus по абсолютному пути:

```powershell
& 'C:\Users\Sergey\AppData\Local\lazarus\lazbuild.exe' 'C:\Users\Sergey\source\repos\Library\Library.lpi'
```

Результат основной сборки — `Prog/Library.exe`; успешная сборка должна
завершиться сообщением `0 errors`. После изменения `.pas`, `.lpr`, `.lfm` или
`.lpi` соберите затронутый проект. Если приложение запущено и EXE занят, сначала
закройте его.

Изменения механизма обновления или release-процесса проверяйте полным скриптом
`scripts/Build-Release.ps1`. Он требует чистого рабочего дерева, собирает
`Library.exe`, `LibraryUpdater.exe`, `UpdaterTests.exe` и `UpdaterProbe.exe`,
запускает тесты версий, JSON, SHA-256, установки и отката, затем проверяет
release-архив. Ключ `-AllowDirty` допустим только для промежуточной локальной
проверки, но не для выпуска версии.

Автоматические тесты покрывают updater; остальные затронутые сценарии проверяйте
вручную: вход, каталог, выдачу, отчёты, настройки и резервное копирование.

## Публикация обновления

Публикация изменений программы начинается только по явной команде пользователя
и считается завершённой лишь после появления проверенного стабильного GitHub
Release. Репозиторий: `https://github.com/sergey-sirenko/Library`, основная ветка
— `main`.

Порядок публикации:

1. Поднимите `APP_VERSION` в `src/uTypes.pas` и синхронизируйте README,
   установочную документацию и релевантный Memory Bank.
2. Завершите локальные тематические коммиты и убедитесь, что исходное рабочее
   дерево чистое. Не удаляйте пользовательские/runtime-файлы ради чистоты без
   разрешения; при необходимости используйте отдельное чистое рабочее дерево.
3. Запустите `scripts/Build-Release.ps1` без `-AllowDirty` и проверьте `0 errors`,
   тесты, состав ZIP и SHA-256.
4. Убедитесь, что архив называется `Library-v<версия>-win64.zip` и содержит в
   корне только `Library.exe`, `LibraryUpdater.exe`, `INSTALL.md`. Каталоги
   данных в архив не включаются.
5. Создайте тег `v<версия>`, отправьте согласованные коммиты `main` и тег.
6. Сразу создайте стабильный GitHub Release для этого тега, приложив ZIP и
   `.sha256`. Не используйте draft или prerelease: приложение читает только
   `https://api.github.com/repos/sergey-sirenko/Library/releases/latest`.
7. Проверьте публичный API: тег, `draft=false`, `prerelease=false`, точное имя
   ZIP, размер и поле `digest` вида `sha256:<хеш>`.

Если push выполнен, но корректный Release не создан, публикация незавершена.
Сообщите о сбое и продолжайте безопасное восстановление, пока стабильный релиз
не станет доступен или пользователь не остановит работу.

## Стиль кода

Используйте Object Pascal в режиме `{$mode objfpc}{$H+}`. Отступ — два пробела,
`begin`/`end` — на отдельных строках, при ошибках предпочтителен ранний выход.
Модули начинаются с `u`, типы — с `T`, константы используют
`UPPER_SNAKE_CASE`. Тексты интерфейса и документация — на русском.

Сохраняйте данные через существующие уровни бинарного ввода-вывода и безопасной
записи. Не меняйте формат `.dat`/`.idx` без необходимости. Удаление логическое,
связи сущностей строятся по внутренним ID.

## Безопасность

Перед публикацией проверяйте отслеживаемое дерево и историю Git на реальные
данные библиотеки, журналы, резервные копии, пароли, API-ключи и закрытые ключи.
Учётные данные `admin`/`admin` предназначены только для первоначального входа и
должны быть изменены при развёртывании.
