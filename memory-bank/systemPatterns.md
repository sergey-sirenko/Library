# Системные паттерны

## Архитектура

- Слой данных загружает `.dat` в память при старте.
- `TLibraryDB` реализует CRUD, бизнес-правила, индексы, журнал и резервные копии.
- UI построен на формах Lazarus: вход и главная форма с вкладками разделов.
- Сетевые функции изолированы от локального хранения и не обязательны для
  основной работы.

## Данные и целостность

- Безопасная запись: временный файл → проверка → замена → повторная проверка.
- Внутренние ID не показываются пользователю; связи строятся только через ID.
- Удаление логическое (`Deleted`, `DeletedAt`, `DeletedBy`).
- Индексы используют нормализованный ключ и ID и перестраиваются при повреждении.

## Внешние сервисы

- HTTPS выполняется через WinHTTP и системный SChannel; сторонние OpenSSL DLL не
  поставляются.
- Не использовать `fphttpclient` с `opensslsockets`, так как это требует
  отсутствующих runtime-DLL.
- OpenRouter и GitHub Updates должны возвращать понятные ошибки и не нарушать
  локальную работу приложения.

## Обновление приложения

- Клиент запрашивает только последний опубликованный стабильный GitHub Release.
- Версии сравниваются как `major.minor.patch`, тег может иметь префикс `v`.
- Ожидаемый asset: `Library-v<версия>-win64.zip` с обязательным GitHub digest
  `sha256:<хеш>`.
- ZIP содержит только `Library.exe`, `LibraryUpdater.exe` и `INSTALL.md`.
- До установки проверяются размер, SHA-256 и состав архива, затем создаётся
  резервная копия данных.
- `LibraryUpdater.exe` ждёт завершения приложения, сохраняет предыдущий EXE как
  `Library.exe.old`, заменяет файл, перезапускает программу и выполняет откат при
  ошибке.
- `Data`, `Covers`, `Backup` и `Logs` updater не изменяет.

## Публикация

- Разработка и тематические коммиты выполняются локально.
- Push и релиз начинаются только по явной команде пользователя.
- Для изменений программы push и стабильный GitHub Release являются одним
  незавершимым процессом: ветка и тег не должны остаться без проверенного
  бинарного релиза.
